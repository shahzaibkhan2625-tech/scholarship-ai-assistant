# ADR-0016: Security Hardening — Redirect-Safe Fetch, Single Operator, Least-Privilege Database Role, Audit Log and Gmail SMTP

> **Scope**: Document decision clusters, not individual technology choices. Group related decisions that work together (e.g., "Frontend Stack" not separate ADRs for framework, styling, deployment).

- **Status:** Accepted
- **Date:** 2026-10-29
- **Feature:** 010-security-hardening (stories 1, 2, 3, 6, 8; `specs/010-security-hardening/plan.md`, `research.md` R1-R10, deviations D-1..D-4 in `spec.md`)
- **Context:** The public server has open sign-up and the full-project audit found these gaps (`spec.md` "Why this feature exists"; Blueprint §19 implementation status). Any signed-up user can approve or reject sources, start monitoring runs and read operational logs (`app/api/sources.py`, `app/api/monitoring.py`, `app/api/health.py`; `User` has no role). A user-supplied URL can make the server request internal addresses such as `169.254.169.254`: `fetch_url` calls `httpx.get(..., follow_redirects=True)` (`app/tools/web_fetch.py:27-32`), and the only guard, `unsafe_url_reason` in `candidate_validation.py`, runs before the request and on `final_url` after it, so a redirect to a non-public address has already been requested and DNS is resolved twice (ADR-0010 decision 2 and consequences (a), (b); accepted again in ADR-0011 Q4 and ADR-0015 decision 1). The app connects as the database owner (`neondb_owner`), which owns every table and can create roles. Nothing records who did what (`audit_log` of Blueprint §14 has no table). Alert email never works because SMTP is not configured, and the existing sender calls `smtp.starttls()` with no context; observed on the installed Python, that default context does not verify the server certificate (`research.md` R7, F-1). ADR-0015 decision 1 put this work first (feature 010). Four owner decisions go beyond the written Blueprint/PRD/ADR text and are recorded as D-1..D-4 in the spec: per-hop address checks including candidate validation (D-1), a wider operator-only set (D-2), auditing operator grants (D-3) and Gmail as the mail provider (D-4). These choices only work together: the operator flag needs the audit log to be accountable, the database role needs the migration split and the audit table's privileges, and the fetch change is what makes the approval-domain rule meaningful.

## Decision

Treat the following as one cluster, because the pieces were designed together and would change together.

1. **Redirect-safe fetch (D-1).** `fetch_url` resolves the host, refuses the request if any resolved address is private, loopback, link-local, cloud-metadata or otherwise non-public (IPv4 or IPv6, including IPv4-mapped forms, numeric encodings and `localhost`-style names), and **connects only to an address that passed the check**: the IP goes in the request URL, the original name stays in the `Host` header and in httpx's `sni_hostname` extension, so TLS hostname verification still uses the real name (https://www.python-httpx.org/advanced/extensions/; `httpcore/_sync/connection.py` reads `sni_hostname`). Redirects are not followed by httpx (`follow_redirects=False`); the code follows `301/302/303/307/308` itself, repeating resolve-check-connect for every hop, at most 5 hops (approved spec assumption), with `trust_env=False`. Only `http` and `https` are allowed. A refused request returns `success=False, blocked=True` and the existing 422 `FetchFailure` path, and is logged with user, entry point and reason. The guard functions move unchanged to a shared module (`app/core/url_safety.py`) and `candidate_validation` re-exports them. The one other outbound call, the API connector, uses the same helper with zero redirects. Source approval additionally requires a public host name (not an IP, not a single-label or reserved/private suffix such as `internal.corp`, not resolving to a non-public address) and maps a duplicate domain to 409. This supersedes the redirect residual risk of ADR-0010 (consequences (a), (b)), ADR-0011 Q4, and the last sentence of ADR-0015 decision 1.
2. **Single operator (D-2).** One operator, the owner. Operator status is a boolean on the user row, read from the database on every request (no role claim in the token, so a revoke applies on the next request). It is granted and revoked only by a command run on the server (`python -m app.services.operator grant|revoke`, same shape as `app.services.retention`); no API route, sign-up field or profile field can set it. A `require_operator` dependency returns 403 "Operator access required" (distinct from 401) on: approve a candidate, reject a candidate, start a manual monitoring run, read a monitoring run's detail (it returns `source_outcomes` built from fetch-log rows, `app/api/monitoring.py:55-61`; owner decision Q-1 = A), read a source's fetch log, and read a candidate's validation results. The run list, the pending-candidate list, source health, coverage and every student route stay open to signed-in users; `/metrics` stays VM-internal (ADR-0011 Q5).
3. **Least-privilege database role.** A role `scholarship_app` created **with SQL** by the owner (not in the Neon console, CLI or API, which add `neon_superuser` membership: CREATEDB, CREATEROLE, BYPASSRLS, REPLICATION; https://neon.com/docs/manage/roles): `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`, created without a password; the password is set with psql's `\password` (prompted, sent as a hash), so no secret is in the script, a variable or a command line. Rights: `CONNECT`, `USAGE` on schema `public`, `SELECT/INSERT/UPDATE/DELETE` on all tables, `USAGE/SELECT/UPDATE` on sequences, no rights on `alembic_version`, and `ALTER DEFAULT PRIVILEGES FOR ROLE <migration role> IN SCHEMA public` so tables the migration role creates later are usable without a manual grant (default privileges apply only to objects created by the named role, https://www.postgresql.org/docs/current/sql-alterdefaultprivileges.html). The script also runs `REVOKE CREATE ON SCHEMA public FROM PUBLIC`, because Postgres 15 changed that default only for new databases (https://www.postgresql.org/docs/release/15.0/). The app uses `DATABASE_URL` on the Neon **pooled** host; migrations use a new optional `MIGRATION_DATABASE_URL` for the owner on the **direct** host (https://neon.com/docs/connect/choose-connection lists schema migrations as a case for a direct connection). The owner URL is passed only to the one-off migration container, never stored in the VM `.env`. The app warns at start if its connected role has owner-level rights, and CI creates the role, migrates as owner and runs the whole suite as `scholarship_app`.
4. **Audit log (D-3).** A new `audit_log(id, user_id, action, entity, at)` table (Blueprint §14 fields) with a closed action set: `user.signup`, `source.approve`, `source.reject`, `monitoring.run.manual`, `submission.approve`, `operator.grant`. Each record is added in the **same transaction** as the action, just before the existing commit, so the action and its record succeed or fail together and a refused action leaves nothing. Only successful actions are audited; scheduled runs are not. For `operator.grant` (no signed-in actor) `user_id` is the grantee. There is no foreign key on `user_id`, and the app role has `INSERT, SELECT` only (`UPDATE, DELETE, TRUNCATE` revoked), so the trail is append-only by privilege. No API route reads it; the owner reads it with owner credentials.
5. **Gmail SMTP (D-4).** Alert email goes through the owner's Gmail account: `smtp.gmail.com`, port 587 with STARTTLS using `ssl.create_default_context()` (verified certificate), username and a Google App Password (16 characters; requires 2-Step Verification) held only in the VM environment, `ALERTS_FROM_EMAIL` the same address (https://developers.google.com/workspace/gmail/imap/imap-smtp; https://support.google.com/accounts/answer/185833). The alert always exists in the app; when mail is unconfigured or sending fails a log line states why (no secrets) and the student-visible `email_error` holds a short code instead of raw exception text.

No new dependency is added: the standard library (`ipaddress`, `socket`, `ssl`, `smtplib`, `argparse`) and existing packages do all of it.

## Consequences

### Positive

- The internal-address path is closed at the fetch itself, for URL match, candidate validation, source approval and the monitor, including redirects and DNS rebinding, instead of by a pre-check that a redirect could bypass.
- Only the owner can change which sources the product treats as authoritative or spend the LLM allowance (Constitution Principle IV; PRD FR-DISC-8), and a revoke takes effect on the next request.
- A bug that reaches the database can no longer create, alter or drop tables or create roles, and cannot edit the audit trail.
- The owner credential never lives in the running container; the password is never typed on a command line.
- There is a durable answer to "who did this and when" for the six security-relevant actions.
- Alert emails can finally be delivered, over a verified TLS session, and students no longer see server error text.

### Negative

- **Pinned-IP fetch can behave differently for some real sites** (SNI, HTTP/2, IPv6-only hosts, virtual hosting); mitigated by tests and a post-deploy fetch of the two monitored sources, with no unpinned fallback built (`plan.md` risk 2).
- Every deploy now has two database URLs and a role script; a forgotten re-run of the script after a migration is caught by CI and the post-deploy check, not by the database.
- The restricted role may expose a statement only the owner role could run; CI runs the suite as the restricted role to find these before deploy (`plan.md` risk 1).
- One operator is a single point of failure: if the owner loses access, recovery needs server access. Revocation is logged but, by the approved list, not audited.
- The `lower(email)` unique index can fail if live data already has two mixed-case duplicates; the deploy then halts for an owner decision (FR-CRED-5).
- Gmail with an App Password ties alert delivery to one personal account, its sending limits and Google's policy (App Passwords are unavailable with Advanced Protection, security-key-only 2SV or work/school accounts, and are revoked when the Google password changes).
- Response size from fetched pages is still not capped, and a permanent owner-only audit read path is not provided (no route); both are left for later features.
- ADR-0010, ADR-0011 and ADR-0015 each need a pointer line; a reader must consult this ADR beside them.

## Alternatives Considered

- **Keep `follow_redirects=True` and check `response.history` afterwards.** That is today's behaviour: the request to the redirect target has already been sent (ADR-0010 consequence (a)).
- **Per-hop check without pinning the connect address.** Closes the redirect gap but leaves DNS rebinding between our lookup and httpx's second lookup (ADR-0010 consequence (b)).
- **A custom httpx transport that resolves and connects.** Possible, but the httpx transports page does not cover pinning; the URL-rewrite plus `sni_hostname` route is the documented one.
- **A third-party SSRF library, or a network egress firewall alone.** A new dependency is not needed; a firewall is a good second layer but cannot return a clear per-request error.
- **A role or `is_admin` claim in the JWT.** A revoke would not apply until the token expires; reading the row each request is free because `get_current_user` already loads it (`app/api/deps.py`).
- **A grant/revoke API endpoint or a "first user is the operator" rule.** Either lets an API call (or a race on open sign-up) create an operator; the spec requires a server-side command only.
- **A fuller role model and review queue.** Out of scope; feature 006 (ADR-0012, ADR-0015).
- **Create the app role in the Neon console, CLI or API.** Those add `neon_superuser` membership, exactly the rights being removed; the Neon roles page describes no way to drop it.
- **Row-level security per table.** The app has no per-role policy model; the problem is schema and role rights, not row visibility.
- **One shared database role for the app and migrations.** That is today's exposure.
- **Pass the role password or the owner URL on the command line or as a psql variable.** Both leak to shell history or the process list; `\password` and `read -rs` avoid it.
- **Audit table with a foreign key to `users`, or update/delete allowed.** A foreign key would tie the record to the account's life or require updates; allowing edits defeats the trail.
- **An audit read API.** The spec says "if any read path exists"; the owner has database access, and a route is an extra surface.
- **Audit by application log lines only.** Not queryable and not in the action's transaction.
- **Another mail provider, or Gmail OAuth.** The owner chose Gmail with an App Password; OAuth needs a token flow the app does not have.
- **Keep the unverified `starttls()` default.** The App Password would travel over a session that does not check the server certificate.
